1 · What "Passk" actually means (and why it's the right target)

The familiar metric pass@k comes from code-generation/LLM evals (e.g. HumanEval): it measures the probability that at least one of k sampled attempts passes — a best-of-k number. The MCP tool-use benchmark MCPToolBench++ uses exactly this for execution success. (arXiv:2508.07575, verified 3-0)

Your requirement is the opposite and stricter. Call it Passk (all-k-agree):

Passk holds for input S ⟺ running the full pipeline on S, k times, in independent processes, yields byte-identical ir.json and byte-identical bytes for every file under surfaces/, and run-1 passes every standard conformance gate (tsc-clean / py_compile-clean / MCP tools.json re-derives / OpenAPI lints clean).

Two halves you need both of:

  • Reproducibility — k runs are identical. For a deterministic generator this is provable by rebuild-and-compare, not statistics. Passk collapses to "the function is pure."
  • Correctness — each run is spec-valid. (k identical-but-wrong runs is not Passk.)
Key insight: the moment an LLM enters the hot path (naming, repair drafting), Passk breaks unless you pin temperature-0 + cache decisions, or freeze a human-approved artifact. Your repair stage is deterministic/offline today — protect that seam.

The distinctive idea: MCP from the SDK, not the spec

Stainless derives the MCP server as a subpackage of the generated TypeScript SDK and offers an "SDK code mode": instead of one tool per endpoint, it exposes just two tools — docs-search and execute-TypeScript-in-a-sandbox. The agent writes code against the typed SDK; context no longer scales with API size. (verified 3-0, docs/mcp)

Their own benchmark on the Increase banking API reports 98% task completeness / 95% efficiency for code mode vs other MCP configs — vendor-reported, not independently reproduced.

For you: Stainless validates IR-fan-out, but couples MCP to TS-SDK internals. Your MCP is a sibling of the SDK off the IR — cleaner for SDK↔MCP round-tripping. You could optionally add a "code-mode" MCP flavor (2-tool) alongside your per-operation tools.json.

6 · OpenAPI Generator & Kiota — the determinism cautionary tale

Kiota (Microsoft, OSS) is the most important external data point for your Passk goal — it proves codegen is non-deterministic by default.

Kiota issue #2442: identical input produced different output across runs. Root cause = randomized hash/dictionary iteration order. Fixed by sorting collections before emit. (verified 3-0, #2442)
Refuted: that idempotency was an advertised design goal — it was a bug they fixed. Lesson: the #1 cause of codegen non-determinism in the wild is unordered map/set/dict iteration — not logic bugs.

OpenAPI Generator (OSS, templated, many languages): use it as a conformance oracle — "does our output for surface X resemble the community-standard shape?" — not as a determinism reference; the same hash-ordering and timestamp pitfalls apply per template.

9 · Determinism engineering — the standards toolkit

9a · Canonicalization: RFC 8785 (JCS)

The formal standard your canonicalize.ts approximates: byte-identical JSON via recursive lexicographic (UTF-16 code-unit) sorting of object keys + canonical number formatting + minimal whitespace. (verified 3-0, RFC 8785) Naming the standard turns "we sort keys" into "we are JCS-compliant."

9b · Reproducible-builds checklist

✅ sort all collections before emit ✅ strip/normalize timestamps ⚠️ fix locale (localeCompare → 'en-US' or code-unit) ⚠️ sort every readdir() ⚠️ pin tool + dep versions ⛔ ban Math.random / UUID / Date in emit

Source: reproducible-builds.org — stable outputs

10 · Research papers & what they mean for your correctness gate

MCPToolBench++ — measuring MCP tool-use (Pass@K)

1,500 queries across 40+ tool categories over 4,000+ MCP servers; metrics = AST, DAG accuracy, Pass@K, Tool-Call Success Rate. Pass@K here measures end-to-end execution success (valid params, correct results).

Use it as: the correctness half of your gate — once a surface is reproducible, run generated MCP tools against a benchmark like this to confirm they actually execute correctly. arXiv:2508.07575 · PDF

DCIChecker — Description-Code Inconsistency in MCP servers

Finds tool descriptions that don't match what the code does (overclaimed/undeclared/misclaimed functionality, undeclared side effects). Direct-Reverse-Arbitration prompting; reports ~96.7% F1 detecting DCI, which affects ~9.93% of real tools. (paper-reported)

Use it as: a lint gate on your mcp.ts output — your tool descriptions are projected from IR summary/description, so a DCI check ensures the generated description matches the generated handler. arXiv:2606.04769

Anthropic — Code execution with MCP

Presenting MCP servers as code APIs (agent writes code) instead of raw tool lists cut a 150K-token workflow to ~2K (98.7%↓). The architectural basis for Stainless "code mode."

Use it as: design rationale if you add a 2-tool "code-mode" MCP flavor to your projection. anthropic.com/engineering/code-execution-with-mcp · Advanced tool use
