Architecture note · API tooling

One hub, two directions:
how we made spec ↔ SDK ↔ MCP bidirectional

Stainless and Fern spent ~2 years building one-way generators (spec → SDK). We built any-to-any conversion in weeks. This document explains the single architectural trick that makes it possible, and proves the three claims behind it.

§1 · Background

Why the incumbents are one-way (a design choice, not a failure)

Stainless and Fern solve a specific business problem: a customer brings an OpenAPI spec; the product turns it into polished, idiomatic SDKs. Nobody ever paid them to go the other direction. Three architectural consequences follow:

Fig. 1 — The incumbent pipeline is a one-way compiler.

1. The IR is output-shaped. Their intermediate representation is packed with language-specific detail (naming conventions, pagination idioms, auth helpers) so the generated SDKs feel hand-written. It is a means to an end — optimized for emitting code, not for being read back.

2. Only writers exist. Every component is of the form IR → output. There is no parser anywhere in the system that consumes an SDK or an MCP server and recovers an IR.

3. MCP sits downstream of the SDK. Stainless builds its MCP server from the generated TypeScript SDK. MCP is therefore the last node in a directed chain — you can never travel MCP → SDK or MCP → spec.

§2 · The architecture

The one trick: a neutral hub, with a reader and a writer per surface

Pick one neutral middle format — plain OpenAPI 3.1 plus a tiny operation-list IR. It is API-shaped, not SDK-shaped: just operations, parameters, schemas, auth. Then, for every surface (spec, SDK, MCP), write two small pieces:

reader: surface → IR   ·   writer: IR → surface

Fig. 2 — Hub-and-spoke with symmetric adapters. The incumbents only have the green arrows.

The big companies only have writers. The new idea is the readers: reverse-derive an IR from an existing SDK (parse the method signatures) or from an MCP server (read its tool schemas — they're already JSON Schema, which maps almost directly onto OpenAPI). Because the middle is neutral, any reader composes with any writer:

SDK-reader  + MCP-writer  =  SDK → MCP
MCP-reader  + SDK-writer  =  MCP → SDK
MCP-reader  + Spec-writer =  MCP → spec   // impossible in their architecture
§3 · Proofs

Three claims, three proofs

Claim 1 · Composability
With N surfaces, writing N readers + N writers yields all N × (N−1) directed conversions — with zero per-pair code.
Proof

Let S = {spec, SDK, MCP, …} be the set of surfaces, |S| = N. For each s ∈ S we write exactly two functions:

reads  : s  → IR
writes : IR → s

Any directed conversion from surface a to surface b is the composition write_b ∘ read_a. Since every reader emits the same IR type and every writer consumes it, all N×(N−1) ordered pairs are covered by the 2N adapters. Cost is linear in surfaces; capability is quadratic.

Contrast: a point-to-point design (which is what "bolt MCP onto the TypeScript SDK" is) needs a bespoke converter per pair — O(N²) code — which is why incumbents never grew beyond one chain. With N = 3 we get 6 conversions from 6 adapters; adding a 4th surface (e.g. Postman collection) costs 2 more adapters and unlocks 6 new conversions. ∎

Claim 2 · Provable round-trips
If the IR is canonically serialized and hashed, "is the conversion lossless?" reduces to a one-line equality test — no manual QA.
Proof

Make the IR deterministic: sort keys, normalize names, strip cosmetic data, serialize canonically, hash with SHA-256. Then for any conversion chain, recover the IR at the far end and compare hashes:

# round-trip: SDK → IR → MCP → IR′
ir  = read_sdk(sdk)
mcp = write_mcp(ir)
ir2 = read_mcp(mcp)

assert ir.hash == ir2.hash   # lossless ⇔ True

Because canonical serialization is injective on IR content, hash(ir) == hash(ir2) ⟺ the two IRs contain identical API semantics (modulo negligible collision probability, ~2⁻¹²⁸ for SHA-256). Every API-shaped fact that left the hub came back. Determinism turns "lossless?" — normally a manual review of generated code — into a single boolean, runnable in CI on every commit, for every reader/writer pair, automatically. ∎

Claim 3 · Weeks, not years
The bidirectional core is genuinely small, because the two expensive things — output polish and perfect reverse fidelity — are exactly the things we deliberately don't build.
Proof (by scope accounting)

Their two years were spent almost entirely on the quality layer of the writers. Our system needs none of it to be bidirectional: readers reverse-derive a good-enough IR (parse method signatures, read tool schemas) and mark it lower-trust. Dropping the perfect-fidelity requirement is the simplification that makes the whole thing tractable — and the hash test (Claim 2) replaces the QA budget. What remains is a neutral IR plus 2N thin adapters: small by construction. ∎

§4 · Summary

The recipe in three lines

To make any tooling ecosystem bidirectional:

  1. Choose a neutral standard as the hub (OpenAPI 3.1 + a tiny operation-list IR).
  2. For every surface, write a reader (→ IR) and a writer (IR →).
  3. Hash the IR canonically so every round-trip is provable in one comparison.
→ any ↔ any conversions · N readers × M writers · built in weeks

Why didn't the big players do this? Not because it's hard — because their business never needed the readers. Their customers arrive holding a spec; the reverse direction has no buyer in their model. The readers are a small amount of code that nobody was incentivized to write. That gap is the product.
